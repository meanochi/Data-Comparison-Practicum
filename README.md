# מערכת השוואת נתוני תקופות עבודה — PDF מול DAT

מערכת שמפענחת ומשווה נתוני "פירוט תקופות עבודה" בין קובץ DAT (ממשק לאוצר)
לבין קבצי PDF (דו"ח סיכום נתוני פרישה), לפי מספר זהות.

המערכת כתובה ב-Node.js.

## התקנה

דרוש Node.js 18 ומעלה.

```bash
npm install
```

## הרצת המערכת

```bash
npm start
```

ואז לפתוח בדפדפן: <http://localhost:5000>
(אפשר לשנות פורט עם משתנה הסביבה `PORT`.)

במסך הראשי מעלים קובץ DAT אחד וכמה קבצי PDF, ולוחצים "בצע השוואה".
במסך התוצאות מוצגת רשימת מספרי הזהות; ליד כל אחד — האם הנתונים זהים, וכמה
תקופות תואמות מתוך כמה. לחיצה על שורה פותחת פירוט מלא של כל תקופה, כולל
הערכים משני הקבצים בכל אי-התאמה.

## הרצת בדיקות

```bash
npm test
```

הבדיקות רצות על קבצי דוגמה פיקטיביים בתיקיית `samples/` שכוללים בכוונה גם
נתונים שגויים (היקף משרה שונה, סוג זכויות שונה, תקופות חסרות ועוד).

## מבנה הפרויקט

המערכת בנויה בשכבות, כך שכל שכבה ניתנת להרחבה בנפרד:

| קובץ                      | שכבה       | תפקיד                                                                                         |
| ------------------------- | ---------- | --------------------------------------------------------------------------------------------- |
| `src/pdfText.js`          | חילוץ גנרי | המרת כל PDF לשורות טקסט בסדר חזותי (mupdf, פונטים משובצים, BiDi) — בלי ידע על מבנה דוח ספציפי |
| `src/parsers/pdfChinuchParser.js` | פרסר דוח   | פרסר דו"ח "סיכום נתוני פרישה": מס' זהות + טבלת פירוט תקופות עבודה                             |
| `src/parsers/datParser.js`        | פרסר DAT   | פענוח קובץ ה-DAT לפי טבלת קודי רשומה (כרגע: 9050)                                             |
| `src/tableSource.js`      | מקור טבלה  | פענוח שורות מהטבלה הזמנית (LD_CHINUCH_9050_TKUFOT_RETSIF) לאותו מבנה תוצאה                    |
| `src/mappings.js`         | מיפויים    | טבלאות הקודים ומיפוי תוויות ה-PDF לקודי ה-DAT                                                 |
| `src/comparator.js`       | השוואה     | מנוע ההשוואה ובניית התוצאות                                                                   |
| `server.js` + `views/`    | ממשק       | ממשק הווב (Express + EJS, עברית RTL) + ‏API‏ (`POST /api/compare`)                            |
| `test/*.test.js`          | בדיקות     | בדיקות אוטומטיות (node:test)                                                                  |

## הרחבת המערכת

**סוג רשומת DAT חדש (9022, 9023...):** ב-`src/parsers/datParser.js` כותבים פונקציית
`parseXXXX(fields, lineNo, result)` ורושמים אותה בטבלת `RECORD_PARSERS` עם
מספר השדות המינימלי. הפונקציה מוסיפה את הנתונים ל-`result` (אפשר להוסיף
אוסף חדש לצד `periodsById`). שורות עם קוד לא רשום מדולגות בשקט.

**פורמט דוח PDF חדש:** יוצרים קובץ פרסר חדש לצד `src/parsers/pdfChinuchParser.js` שקורא
ל-`extractVisualLines(buf)` מ-`src/pdfText.js` ומגדיר רק את הרג'קסים ומבנה
השורות של הדוח החדש. כל הטיפול בפונטים, ב-BiDi ובקיבוץ השורות כבר נעשה
בשכבה הגנרית. לבניית רג'קס מול עברית חזותית משתמשים ב-`toVisual("טקסט לוגי")`.

**תווית חדשה בדוח הקיים:** מוסיפים אותה ל-`PDF_TKUFA_LABELS` או
`PDF_ZCHUYOT_LABELS` ב-`src/mappings.js` עם קבוצת קודי ה-DAT המתאימים.
עד אז המערכת מסמנת אותה כאי-התאמה עם אזהרת "נדרש עדכון מיפוי".

**השוואה מסוג חדש:** מוסיפים פונקציה ב-`src/comparator.js` לצד
`compareId`/`compareAll`, על נתונים שהפרסרים החדשים מחזירים.

### הערה טכנית על חילוץ ה-PDF (`src/pdfText.js`)

חילוץ הטקסט נעשה עם ספריית mupdf ברמת התו הבודד: כל תו נאסף עם קואורדינטת
ה-X שלו, השורות מקובצות לפי קו הבסיס (Y) על פני כל העמוד, והתווים ממוינים
משמאל לימין — כך שמתקבל תמיד הסדר החזותי שעל הדף, זהה לפלט של pdfplumber
בגרסת הפייתון, ללא תלות בסידור ה-BiDi הפנימי של ספריית החילוץ. בנוסף,
פונטים מסוג Type0 ללא טבלת ToUnicode (כמו בדוחות האמיתיים) מפוענחים דרך
קריאת טבלת ה-cmap מקובץ הפונט המשובץ והיפוכה למיפוי גליף→תו.

## פורמט קובץ ה-DAT

קובץ טקסט מופרד ב-`~`, בקידוד עברי ישן (DOS/IBM-862; המערכת מזהה גם
ISO-8859-8 ו-UTF-8). מפוענחות רק שורות שמתחילות ב-`9050`:

| מיקום בשורה | שדה         | פורמט                                   |
| ----------- | ----------- | --------------------------------------- |
| 4           | מספר זהות   | כולל אפס מוביל                          |
| 6           | סוג תקופה   | קוד מטבלת CODE_SUG_TKUFA_GOLMI          |
| 7           | תאריך התחלה | DDMMYYYY                                |
| 8           | תאריך סיום  | DDMMYYYY                                |
| 9           | אורך שירות  | חודשים × 100 (למשל `01200` = 12 חודשים) |
| 10          | סוג זכויות  | קוד מטבלת CODE_SUG_ZCHUYOT              |
| 11          | היקף משרה   | × 1000 (למשל `0667` = 0.667)            |

שאר השדות בשורה אינם ידועים בשלב זה ואינם מושווים.

## התממשקות דרך API — טבלה זמנית במקום קובץ DAT

המערכת הקיימת טוענת את קובץ הממשק עם SQL*Loader (קובץ הבקרה `LD_Chinuch.ctl`)
לטבלאות `LD_CHINUCH_*`. במקום להעביר לנו קובץ DAT, היא קוראת ל-API שלנו
**אחד-על-אחד**: כל קריאה נושאת את שורות טבלת
`LD_CHINUCH_9050_TKUFOT_RETSIF` של תעודת זהות אחת + מסמך ה-PDF שלה
(DDL מלא ל-Oracle: `sql/LD_CHINUCH_9050_TKUFOT_RETSIF.sql`):

```
POST /api/compare
Content-Type: application/json

{
  "rows": [
    { "MISPAR_TNUA": "9050", "MISPAR_ZEHUT": "012345678", "SUG_TKUFA": "9999",
      "TAARICH_ME": "01092010", "TAARICH_AD": "31082015", "ORECH_SHERUT": "06000",
      "SUG_ZECHUYOT_LEGIMLA": "02", "HEKEF_MISRA": "1000", "SEQ": 1 }
  ],
  "pdf": { "filename": "report_12345678.pdf", "content": "<PDF בקידוד base64>" }
}
```

- `rows` — שורות הטבלה של אותה ת"ז, כאובייקטים ששמות העמודות הם המפתחות
  שלהם (כפי שמוחזר מ-`SELECT` על הטבלה). עמודות שאינן משתתפות בהשוואה
  (`KOD_PEULA`, `ZIHUY_NOSAF`, `SEMEL_MISRAD`, `LOAD_DATE`) מותרות ומתעלמים
  מהן; עמודת `SEQ` משמשת לזיהוי השורה בהודעות שגיאה ואזהרה. בקשה עם `pdf`
  בודד שמכילה יותר מת"ז אחת נדחית עם 400.
- `pdf` — מסמך סיכום הפרישה של אותה ת"ז, שם + תוכן ב-base64.

גם מסך ההעלאה עובד כלקוח של ה-API: הוא מקבץ את שורות הקובץ לפי ת"ז ושולח
קריאה נפרדת ל-`/api/compare` עבור כל מסמך שהועלה — בדיוק כמו המערכת
הקיימת. ת"ז שיש לה שורות אך לא הועלה לה מסמך מדווחת כאזהרה, ללא קריאה.

מבנה התשובה (לפי האפיון):

```json
{
  "valid": 1,            // אינדיקציית תקינות: 1 - הכל תואם, 0 - אחרת
  "idNumber": "12345678",// הת"ז שנבדקה (במצב אחד-על-אחד)
  "text": "...",         // טקסט מאוחד המרכז את כל התוצאות והפערים
  "summary": { ... },    // מונים: total / match / mismatch / missing / error
  "warnings": [ ... ],
  "results": [ ... ]     // הפירוט המלא (מה שמסך התוצאות מציג)
}
```

הפענוח נעשה ב-`src/tableSource.js`, שמחזיר בדיוק את אותו מבנה תוצאה כמו
פרסר ה-DAT, כך ששאר שכבות המערכת משותפות לשני המקורות.

### בדיקות ידניות ב-Postman

`node examples/makePostmanCollection.js` מייצר את
`examples/postman_collection.json` — קולקציה עם 9 תרחישים (תקין מלא,
אי-התאמות, שדה `pdf` בודד, ומקרי קצה: חסר `rows`, חסר `pdf`, קובץ פגום,
`rows` ריק, שורה לא מספרית), כולל Tests מוטמעים שמאמתים כל תשובה.
מייבאים את הקובץ ל-Postman ומריצים כשהשרת פעיל (`npm start`).

### סימולציה מקומית של התהליך המלא

אפשר לשחזר מקומית את מה שקורה במציאות — טעינת ה-DAT לטבלה אמיתית לפי
הלוגיקה של `LD_Chinuch.ctl` ואז שליפה ושליחה ל-API (דורש Node 22.5+,
טבלת SQLite מקומית ב-`examples/chinuch.db`):

```bash
node examples/simulateCtlLoad.js      # "sqlldr": טעינת samples/sample.dat לטבלה
npm start                             # בטרמינל אחד
node examples/apiFromTable.js         # בטרמינל שני: SELECT מהטבלה -> API
```

ולהדגמה של התהליך המלא כמו בתפעול (בסגנון ControlM): מנטרים תיקיית קליטה,
וכל קובץ DAT שנוחת בה נטען לטבלה ונשלח ל-API אוטומטית:

```bash
npm start                                  # טרמינל אחד
node examples/watchAndSend.js              # טרמינל שני: ניטור examples/incoming/
cp samples/sample.dat examples/incoming/   # טרמינל שלישי: "הגעת קובץ"
```

קבצי PDF שמונחים בתיקיית הקליטה נשלחים יחד עם הקובץ (אם אין - נשלחים קבצי
הדוגמה); קובץ שטופל מועבר לתת-תיקייה `processed/` עם חותמת זמן.

**מעקב אחרי התהליך:** `node examples/showTable.js` מציג את תוכן הטבלה
(כמה שורות, מתי נטענו, פילוח לפי ת"ז) - הוכחה שהטעינה קרתה; השרת רושם
ללוג כל בקשת `/api/compare` שמתקבלת (כמה שורות ו-PDF, תוצאות, משך) -
הוכחה שהנתונים הגיעו; ואם מגדירים `API_DUMP_DIR=נתיב`, השרת גם שומר שם
את גוף כל בקשה כקובץ JSON לתחקור.

## כללי השוואה שסוכמו

1. **התאמת שורות** לפי (תאריך התחלה, תאריך סיום); לאחר מכן מושווים סוג
   תקופה, אורך שירות, סוג זכויות והיקף משרה. עמודת "מקדם אם" שב-PDF אינה
   קיימת ב-DAT ולכן אינה מושווית.
2. **עזיבה:** שורות DAT עם סוג תקופה 4 אינן מודפסות בדו"ח ה-PDF, ולכן אינן
   נספרות בהשוואה — הן מוצגות במסך התוצאות לידיעה בלבד.
3. **שבתון:** תווית "שבתון" בעמודת סוג תקופה ב-PDF תואמת ב-DAT לקוד סוג
   תקופה 2 (חל"ת) בשילוב קוד סוג זכויות 67 (שבתון מורים).
4. **תוויות מרובות-קודים:** למשל "לא נושא זכויות" ב-PDF יכולה להתאים לקוד 10
   או 13. תווית שלא מוכרת למערכת מסומנת כאי-התאמה עם אזהרה מפורשת לעדכן את
   המיפוי ב-`src/mappings.js`.
5. **מספרי זהות** מנורמלים ללא אפסים מובילים (ב-PDF מודפס בלי אפס מוביל).
6. **בדיקת שפיות:** אם נמצאות לאותה ת"ז שתי תקופות עם אותם תאריכי התחלה
   וסיום — מוצגת אזהרה (לא אמור לקרות).
